UnodeAi 0.9.97

Accountable AI teams, under your direction.

From vibe coding to vibe engineering. Vibe coding: you ask, the AI says “done”, and you hope. Vibe engineering: every agent has a role, enforced limits, and a record you can check.

UnodeAi organizes AI agents into a team for engineering, design, marketing, sales, compliance, finance, operations and more. A project manager agent delegates the work. You can follow every task, approve or refuse what an agent asks to do, stop it, and export the record from request to result.

An agent saying “done” is never evidence. UnodeAi keeps what an agent claims apart from what UnodeAi saw happen. It records whether an objective check ran and passed. Where judgment is needed, a person can record the verdict. You can put different models and providers on one team and have one review another’s work, under roles and permissions you set.

Delegate with confidence: your direction, a record you can audit, and no result called verified until it has passed a check.

It runs in VS Code, Cursor and Devin with your own providers and keys. There is no telemetry and no network call at activation. A SHA-256 is published for the exact bytes you install.

Quick Start

  1. Install UnodeAi from Open VSX (search UnodeAi in Extensions), or from a .vsix file. Cursor's marketplace mirrors Open VSX and can lag behind it by a varying amount. At the 0.9.33 release, the new version was still not offered 40 minutes after publication, but it was being served 6 hours later. Version 0.9.34 was installable 27 minutes after publication, 0.9.36 within 42 minutes, and 0.9.41 within the hour it shipped. Expect a delay of minutes to a few hours. If a version is missing right after a release, treat it as the mirror catching up, not as a broken install. To get it immediately in Cursor, use Ctrl+Shift+P → Extensions: Install from VSIX.... UnodeAi is not on the Microsoft VS Code Marketplace. After you replace an installed version, fully quit and reopen the editor. A reload is not always enough.
  2. Run UnodeAi: Run Setup Wizard.
  3. In the wizard, choose an OpenAI-compatible connection, Claude CLI, or Codex CLI.
  4. Create a team in the wizard, then select Finish and continue.
  5. If a team exists, Finish opens the Workbench. Otherwise, it opens the create-team path in the Team panel.
  6. Send a goal to the Project Manager in the Workbench.

Before you save, each available setup door shows its runtime, billing path, and egress summary. OpenAI-compatible connections include Unode, Roam, OpenRouter, OpenAI Compatible API, and any named custom gateways. To create one without leaving the wizard, select ＋ Add custom gateway… in that menu. The host collects the gateway's display name, HTTPS endpoint, and masked key in native prompts. It then selects the new gateway. The key never enters the wizard webview. The Claude and Codex setups pre-fill their login command in a terminal but never run it.

Project files cannot grant execution authority

Update to 0.9.81 before running agents from an untrusted repository. Earlier releases let .unode/team.json supply a provider process environment and the legacy automatic-approval flag. On Windows, a Claude or Git command started by the host could also resolve to a planted program in the working folder. VS Code and Devin required trust first. Cursor does not provide that trust step.

Team files now keep inert data: identity, prompt, and registered route and model. They can only narrow tool, folder and command scope. UnodeAi ignores these settings, shows one notice, and does not write them back: process environment, automatic approval, backend/base-URL/restart/cwd choices, executable Skills/Playbooks, and MCP process/grant configuration. Reapply trusted capabilities and integrations through Build an Agent. For UnodeAi-hosted and Claude approvals, use the Commands and Writes selectors in the Workbench. Codex shows its native permission profile instead. Programs that UnodeAi starts resolve to absolute host paths outside workspaces and worktrees. This includes approved stdio MCP programs used by either backend route. Literal commands that you approve keep their normal project-relative behavior.

Upgrade behavior: the first activation of 0.9.81 removes only env and autoApprove from saved agents whose source is unknown. Existing Skills, Playbooks, MCP grants, routes, backend choices and other user configuration stay intact. A legacy project integration is imported only when its exact launch configuration was already approved in this workspace. The notice names the integrations it imported and the unapproved project entries it ignored. MCP state moves to unode.approvedMcpServers / unode.hostMcpServers.v1. If you downgrade to 0.9.80, you must approve integrations again.

Project state is root-bound in 0.9.82. An editor may reuse its extension-storage bucket for another project. Even then, rosters, transcripts, checkpoints, runs, policy, integration evidence, and MCP approvals/configuration cannot carry over into that project. Changing the root clears the live agent selection and presentation state. Existing VS Code and Cursor state is imported only for the same proven root. Old Devin history is deliberately not imported. Reset Workspace State affects only the current root.

One network-consent decline ends the request. On an OpenAI-compatible route, the decline happens before any request is sent. It skips transport retry, request-body recovery, and streaming fallback. The dialog does not appear again in the same turn.

Teams and Roles

The default software crew is Project Manager, System Architect, Senior Developer, and Reviewer. The Software group in the picker also offers the Software Engineering Team. It is that crew plus QA Engineer and Technical Writer as first-class seats. With the standalone Solo that every team ships with, it has seven agents. You can also add QA, DevOps, Technical Writer, Security, Data Engineer, Product Manager, Solo, and knowledge-work specialists one at a time. The catalog contains 52 role templates and 25 team presets. They include Contract & Compliance (contract analyst, privacy officer, GRC and procurement analysts) and Website Design & Development (product designer, frontend engineer, content strategist, SEO specialist and QA). In the compliance preset, every output stops where a person with authority must decide. Sanctions or export-control questions are refused and routed, not answered.

Beyond the software crew, the team picker offers ready-made knowledge-work presets: Business Planning, Business Analysis, Financial Analysis, Marketing (content, growth, research, SEO/analytics), and Sales (SDR, account executive, sales engineer, customer success). They use the same PM orchestration, with non-code specialists and team rules geared to analysis. If a roster already exists, choosing a preset offers Keep current team, Add to current team, or Replace current team. Add keeps the roster and appends the preset. Saving a team for one project or for all of them

Create/Save/Load a Team is the one home for saved teams. Its Saved teams section starts with Save current team… and then lists named project and personal saves. Saving offers Save to This project, Save to All projects, and Cancel. The result names that same scope and location. Only named saves have a trash button. System defaults never do. The delete confirmation names the scope. This project deletes .unode/teams/<name>.json (and its host-owned fingerprint), so people who receive that file through Git lose the save too. All projects deletes only the personal library. The running team is unaffected. Automatic snapshots have their own delete action in Restore a previous team….

A saved team file never grants execution authority by itself. A This project save records the exact file bytes and path in UnodeAi-owned storage. When you open that save unchanged, UnodeAi shows one confirmation for the whole team. It lists each agent and offers Restore saved permissions or Load read-only. An edited, copied, or cloned file loads read-only. It then opens a review for each agent, with every extra permission unticked. Restored tools stay capped at the file's saved ceiling. Teams saved before 0.9.87 have no fingerprint. For them, the surviving primary skill and the role template's skills are offered unticked, capped at the old saved ceiling. Save such a team once again in 0.9.87. When an unticked review restores selected permissions, the completion notice says how many agents got them back. It calls the team read-only only when no agent did. Restore a previous team… opens the automatic snapshot made before a roster replacement.

A folder permission is kept only if it lands inside the workspace you are opening it in. This is checked after the path is resolved and symlinks are followed. MCP grants, tool/edit protocol choices and process settings stay host-owned. They are never imported from the file. Skills and Playbooks in a project save are inert declarations until the confirmation or the unticked review. An agent's env and legacy autoApprove are neither written nor loaded. Re-select trusted integrations in Build an Agent. The Workbench shows Commands/Writes for UnodeAi-hosted and Claude approvals, and the native permission profile for Codex.

Build your own agent

Every section carries its own Advanced fold, and folds start closed. No fold opens by itself. A closed section stays closed until you click it. Skills and Tools show what is selected and fold the rest into a full list. Model fine-tuning comes before them. Double-clicking a team member opens that agent’s Workbench conversation.

Run UnodeAi: Build an Agent to open the Agent Builder. It is a form to create or edit a custom agent (name, a built-in or custom role like CEO, icon, model, system prompt, capability tools, folder access, and MCP grants) without touching JSON. A new agent opens blank, with Select a role… in the Role dropdown. Picking a role is what fills in the name, instructions, icon, model, and default skills. You can then change all of them. The chosen connection has the final say. Tool skills and MCP grants it cannot use are disabled with an explanation, and the host rejects forged or hand-edited requests. If a role switch replaces instructions you wrote yourself, one click restores them. If you save without restoring them, the replaced text is still kept as the agent's undo record. You can attach any number of skill playbooks from the skill library. These are market-proven procedures (OWASP review, dependency-risk triage, test-coverage gaps, accessibility audits…). The instructions get only each playbook's name and its when-to-use line. The full procedure is loaded on demand, when it is actually relevant. This way, the agent starts out knowing how to do the job without carrying every procedure in its prompt. The in-app library stays small. For the long tail of other skills, the builder links out to the full skill library. When you save, the agent joins your team like any preset.

Skill Playbooks and MCP grants work on both CLI routes. Claude and Codex load the selected instruction-only Playbooks through their native Skill mechanisms. They load them from a temporary per-agent root that the extension owns. A Playbook never grants tools or widens the sandbox. An executable action can select only a handler compiled into the installed VSIX. Skill folders and remote catalogs cannot contribute code. Every run requires Workspace Trust plus a fresh approval bound to the digest. No bundled Skill currently exposes an action. The manifest in the manual is only an example of the format. For managed MCP, the extension host stays the external client. It exposes only the agent's approved tools, through a local bridge or App Server dynamic tools. It rechecks the live grant when a tool is called, and it shows startup grants that are unavailable. It does not add grants or secrets to the global configuration of either CLI. UnodeAi's own Claude bridges get unpredictable names for each session. Only their exact tool names are allowed automatically, so a native server named like a UnodeAi bridge gets no special treatment.

Managed-integration lifecycle is visible and revocable. Each starting agent has its own 45-second deadline to become ready. Agents that start at the same time share one mount without cancelling each other. A missing or empty secret fails before the server starts, and the error names only the variable. The Integrations tab in the Marketplace lists configured custom and catalog integrations with their connection state, failure reason and granted agents. An MCP protocol error is recorded as an integration failure, even when it contains text. UnodeAi does not reconnect the server if it still responds. A stdio connection failure includes the last part of stderr, as size-limited plain text. Only values resolved from SecretStorage are redacted. Ordinary literals such as DEBUG=1 stay readable. Removing an integration names the affected agents and revokes saved and live grants. It cancels active calls and removes configuration and approval state, but it does not delete shared secrets. A cancellation before dispatch counts as cancelled. After dispatch, a cancellation or timeout counts as outcome unknown, and the late result is discarded. In that case, the connection is quarantined while UnodeAi automatically reconnects through the same approved mount path. Calls made during recovery wait or report that the server is temporarily unavailable. They never report revoked consent.

Native Codex MCP remains Codex-owned. Its calls appear in chat with server, tool and status only. They are explicitly labelled as governed by Codex and not mediated by UnodeAi. They never count as UnodeAi evidence. If a Codex agent's team tools or managed-integration tools change, App Server cannot resume its thread with a different tool surface, because a thread's tool surface is immutable. Instead, UnodeAi visibly starts a fresh Codex conversation. The previous App Server thread is not deleted, and the UnodeAi transcript remains. However, the new model conversation does not inherit the model context of the old thread.

Tool calling method. Auto starts with native tool calling. The builder shows a warning for model families that have leaked tool calls as text. With those models, the first tool use may visibly retry while UnodeAi switches to XML for that session. Tool following may also be weaker. This is a warning, not a block. Native and XML remain explicit choices, and you can still type any model id by hand.

Workbench, Transcript, Plan, and Act

Codex CLI uses a consent-gated local App Server. UnodeAi first runs bounded local checks of the version and login status. Before App Server or a model request starts, the prompt names OpenAI and the model provider configured in Codex. UnodeAi does not control its network destinations. This grant is separate from ordinary OpenAI API consent. It is bound to the canonical executable path, so if you change binaries, UnodeAi asks again. In Act mode, each agent offers Ask for approval (default: workspace-write, on-request, user review, network off), Approve for me (Codex auto-review with a visible chat trail), and Full access (unsafe), which you must confirm separately. Full access removes the sandbox, enables network, has no approval prompts, and records no UnodeAi checkpoints. Under Ask, routine commands and workspace edits run without a card. When Codex requests an escalation (sandbox, network, permission, or an MCP call it routes for approval), you are asked. An MCP tool that Codex calls from inside its own exec code tool is not routed for approval. An agent with explicit Folder Access grants cannot use Full access. Routine Codex edits are not UnodeAi checkpoints. Plan mode and host ceilings use read-only. In Plan mode a Codex agent reads files with UnodeAi's read_file, because Codex reads files only by running commands. Native Codex features remain available after consent. You can use Codex CLI 0.155.0 or newer. Windows validation records 0.155.1. Newer versions must pass live protocol and policy checks. When you open the executable chooser, it lists verified npm/user installs before PATH. In a new editor, Load models from Codex runs a short-lived App Server that only lists models. It runs from extension storage, not the workspace, and is then stopped. Folder Access controls effects, but it is not a sandbox for workspace reads. Codex may read files available to the Windows user and send selected content to its configured provider.

With cached account models, Agent Builder keeps Refresh models from Codex available. Only clicking the button requests the list through the existing executable/login checks and consent; opening the picker does not. Refreshing does not update Codex or grant access to models the selected CLI does not return. The line under the model field then says how many models that Codex version returned, or why none were loaded, until the next load.

Codex preserves its native intelligence and can lead a team. The UnodeAi role is added as a developer instruction. It does not replace Codex's base instructions. A bounded agent with write uses workspace-write. Without write, it is read-only. execute is not a separate Codex switch, because commands always run inside the selected native sandbox. The host may select Claude or Codex as the coordinator. Only that agent receives team tools, and a role label cannot grant them. Codex also supports steering an active App Server turn.

Repository CLI configuration is content-bound. Project configuration in .claude, .mcp.json, and .codex can sit in the agent working directory or in a folder above it that the native CLI searches. Before either CLI starts, UnodeAi shows a redacted trust dialog for it. Because folders above the working directory are checked too, opening only a subfolder of the repository cannot bypass it. HOME .claude and .codex remain user configuration that is not inspected. If the content changes at all, UnodeAi asks again. Trust and load enables the project layer with a trusted override that is local to the process. Continue without project automation disables it with an untrusted override. Neither choice edits the user's Codex configuration.

Automatic refresh is user-controlled. The only scheduled network task is the daily price refresh. Roam and Unode each have their own toggle (the Automatic daily price refresh checkbox on each provider card). Unbound unode.pricingSources has a separate global toggle. Scheduled requests never run at activation and never prompt. Triggers that fire at the same time are merged, and requests back off after a failure. They contact only a metadata host that was already approved.

Claude CLI agents stream partial text and thinking during a turn. Their native tool results fill in the same tool cards that OpenAI-compatible agents use. Before any Claude native tool call runs, a fail-closed hook mediates it. This includes calls made inside Claude's own subagents. Each Claude agent keeps its own hook files in its own folder under .unode/claude/, so agents that share a working folder never use each other's hook files.

Workbench is the editor-first conversation surface. UnodeAi: Open Workbench starts work in one native editor tab, or reveals it if it is already open. The tab has one agent selector, a compact role/route/model/cost header with the context meter at its right end, a full-width transcript, and a composer pinned at the bottom. You can move it with the normal editor-tab drag targets and close it like any native tab. Reopening restores the same host-owned session and never starts or duplicates a backend turn. The changed-files command opens an Edit history rail; its × or Escape closes it. Restored entries remain as history, and they do not falsely show as still changed.

Select code or text in an in-scope editor or a UnodeAi diff. Then choose Add to UnodeAi from the editor lightbulb. This places the selection in the selected agent's composer. It is not sent until you send the message. The action is absent when no team agent is selected. It cannot turn an outside file into context unless that agent's existing Folder Access read scope already allows it.

Local project discovery names its reach before it uses it. In a trusted workspace, unode.localReadScope can be workspace, parent (the default), or volume. The first time a top-level request makes the crew read, list, search, or inspect a Git tag through the root outside the workspace, UnodeAi shows the root's resolved absolute path. The modal says that a search may walk the entire tree. It also says that returned names and content may reach the configured model provider. For a volume, it warns that the volume can include other users’ profiles. If you decline or dismiss it, that root is blocked for the coordinator and its delegates during the current request. Immediate retries do not ask again, but a later direct request from the user may. A dialog that fails also blocks retries within that request, but it is not recorded as the user’s decision. The refusal offers Grant folder access. The Security panel lists the session-only grant/revoke state. Writes, deletes, shell commands and Claude native file access stay in the working folder. Folder Access can still narrow the result. The tool card and run evidence keep only an opaque root id, the action and a count. They never keep a path, query, filename or file contents.

If a turn cannot run yet, the shared Workbench transcript renderer says why and offers one next action: Create a team when there are no agents, or Open Settings when no connection is available or its API credential is missing. The host checks readiness without sending endpoint, secret-name, or credential details to the webview.

The compact Team sidebar is for navigation and status. Session rows come first, and each shows the agent's current responsibility. A row stays one line until you ask for more. When you hover over it, that agent's controls (Stop/Start, Restart, ⚙️ Configure, Terminal, Remove) replace the status word. The ▾ chevron expands the row in place to show the model, live context/cost/turns, skills, and changed files. Since 0.9.93, an expanded row shows Provider, Role, Status and Reasoning in one strip. The strip is two rows of two in a narrow sidebar and one row in a wide one. Reasoning is the baseline the agent is configured with. It shows a value, Provider default, or Not supported on a route that does not take the setting. An expanded row's controls are always visible, and its ⚙️ Configure control opens the agent's Agent Builder page. An expanded row carries no status word. The first glyph shows the status, and the dot on the agent's icon distinguishes working, idle, stopped, and error. The title bar shows the version beside the title. It pins Open Workbench, Add Agent, ⋯ Team Actions, Settings, Message, Solo, and Collapse/Expand. ⋯ Team Actions lists everything that is not pinned (Build an Agent, Create/Save/Load a Team, Marketplace, Start/Stop All, Team Rules, Restore File Checkpoint, concurrency mode, Security, Evidence Report). When you narrow the sidebar, the collapsed agent chips wrap instead of scrolling out of sight. The Chat sidebar view (unode.chat) is a compact alternative entrance to the same responsive transcript renderer. It is not a second main surface. Both containers can be open, and only visible containers receive live updates. unode.workbench.autoOpen defaults to true for chat and session actions. It never opens a Workbench just because UnodeAi activated. Turn it off if you prefer the sidebar. Use UnodeAi: Toggle Workbench Composer Focus (Ctrl+Alt+Enter, or Cmd+Option+Enter on macOS) to move between the Workbench surface and the composer.

Changed files. The Show Changed Files icon in the Workbench title bar opens a rail. The rail lists what the selected agent changed, newest first. Each entry opens that edit in the native VS Code diff editor (side-by-side or inline, F7 navigation, folded context, and the live file on the right so you can type a correction into the diff). ⟲ restores that one file after you confirm. A restore is checked as a new write when you ask for it: it acts on the file the agent changed (its worktree, Folder Access subfolder or workspace folder, named in full in the confirmation), needs a trusted workspace, refuses a file with unsaved editor changes, and refuses a file that no longer holds what UnodeAi last recorded, so newer work is never rolled back. The confirmation counts every recorded edit it undoes, by agent. An edit recorded by an earlier version, a deleted folder, and a file that was not UTF-8 text are listed with restore disabled. See Restoring a file in the manual. The rail starts closed and remembers its state for each workspace. In a narrow editor, it becomes an overlay drawer instead of hiding, so the title action never says Hide Changed Files while nothing is on screen. Worktree lane diffs use the same editor. A lane-level view asks which changed file to open. The base side is pinned to the commit the tab was opened against (named in the title), so an open diff never re-points when the base branch moves. The diff inside an inline tool card is unchanged. An approval keeps its diff attached to the decision.

Approvals stay inline with the command, URL, or diff they decide. They are not moved into a separate queue. While a decision is pending, its card reserves the measured height of the floating composer, but only while the card is visible, so you can scroll the decision fully above the dock without leaving a permanent gap in the transcript. The status bar shows 🔐 N waiting. The UnodeAi activity container shows the same count, and the affected Team row is locked. Click the status-bar item or the row to open the relevant Workbench transcript and scroll to the existing card. Agent requests never steal focus, autofocus an allow button, or expand a UnodeAi sidebar you collapsed or switched away from. While a card or approval dialog is actually open, its agent shows Waiting on your approval, not Stalled, on every route. A request that the policy decides without asking you never shows this status. Each approval is decided once (0.9.88): your click, its 15-minute window running out (a denial), or Stop, whichever comes first. Anything later is ignored before it can take effect. A dialog answered after its window closes therefore grants and saves nothing. Stop removes that agent's cards at once, and its worker receives a denial. Another agent waiting on the same approval keeps its card. consent_required is a waiting state, not an error. An expired approval stays visible as Denied — timed out. Public-web approvals give a person a 15-minute window. This window is independent of the fail-closed local transport clock.

A prompt that stops work plays one short chime when it appears (0.9.88): an approval card or dialog, or a consent dialog such as a new model-network destination, Codex's network access, a repository's CLI configuration, a media upload, a folder outside the workspace, a coordinator brief to another provider, or a managed integration that needs your go-ahead. It does not sound again when you answer or when a second agent joins the same approval. Nor does it sound for dialogs you opened, completion notices, or decisions the policy made without asking. It needs one interaction first: VS Code lets a chat view play sound only after you have typed or clicked in it since it opened. As a result, the first prompt after VS Code starts is silent, and so is any prompt that appears while no UnodeAi chat view is visible. The prompt itself always appears normally. A missed sound is noted once in the output log. Turn it off with unode.attentionSound. That setting is read from your user settings only.

Rework is bounded until you write. When a delegate replies to a rework request, the reply wakes an idle PM. The PM reviews it and reports to you. After your last message, UnodeAi sends at most two rework requests per task. A third is recorded but not sent, and the chat says that automatic rework has stopped. Your next message to the PM allows further rounds.

Every agent has a persistent chat. The Workbench transcript supports live streaming, Stop, Steer, tool cards, diffs, command output, analysis cards, context usage, todos, approvals, and import/export. Clear deletes a transcript. Archive hides it without deleting it (restore it later with View Archived Chats). Agents can also search_files (regex → file:line) and delete_file (sandboxed + checkpointed) so they don't resort to scratch scripts or blocked shell tricks.

The context meter says where its denominator came from, and a separate button acts on that. The meter sits at the right end of the Workbench header bar. In the Chat sidebar, it sits beside the Compact button below the message box. It reads like 41% of an assumed 1,048,576 tokens. The ⤄ icon button in the row of controls below the message box compacts when you click it. The reading is labelled configured (you typed it), measured (the gateway advertised it through the consented model-list read), provider-refused (a request that size was rejected), or assumed (the documented fallback). Clicking the button compacts now, whether or not the automatic trigger has been reached. On an OpenAI-compatible agent, UnodeAi summarises the older turns. It keeps the newest turns and every record of work word for word. On a Claude or Codex agent, it asks the runtime to compact its own conversation. A receipt in the chat reports the result, or says plainly that nothing could be compacted.

A coordinator can end work it cannot finish. close_assignment takes complete, partial, or blocked. The last two require one entry for each undelivered item, with a concrete reason. complete is refused while any settled delegation still has no recorded decision. partial and blocked are outcomes to report, not failures to hide. Before this existed, the vocabulary covered only a result returned by a delegate. A coordinator given an impossible job had no terminal state and simply stopped. If an assignment ends with no conclusion, UnodeAi appends one itself. It is labelled as UnodeAi’s, not the coordinator’s. It carries only mechanical facts and never a claim about whether the work was correct.

Every finished team job gets one Job outcome card (0.9.93). When a coordinator’s job closes, Chat shows a Job outcome · Host-observed card right after its final reply, in the sidebar and in the Workbench. Its summary line reads like Complete · Verified · 1 file changed · 1/1 checks passed · $1.42 estimated · 40s. The line also names what is left over, such as 1 task unfinished. When you open it, it shows eight sections: Outcome, Work, Changes, Checks, Remaining, Usage, Approvals and Timing. Every figure is something UnodeAi recorded while the job ran. Nothing is taken from what an agent wrote. Showing or opening the card runs nothing. Verified appears only when a check declared for the task was seen to pass. The card says plainly what was not recorded. A missing price is cost unavailable, never $0. Amounts on different bases are listed separately and not added together. Approvals read None recorded, with a note when a turn waited for a person on a consent dialog that is not an approval. The card is not a message. It is never sent to a model, summarized, compacted or counted as tokens. After a reload, it appears in the same place. A fact that arrives late updates the card in place.

A stopped task makes its job partial, and the job ends there. If any task in a job was stopped or interrupted, the job is Partial, no matter who closed it. If you stop the last running task of a job while its coordinator is idle, the job ends at that moment. The card appears at once under the coordinator’s last reply in that job. Its elapsed time is counted up to the moment you stopped the task. The card’s actions are Review changes, Open evidence, Continue unfinished work and the spend actions Change target and Reset counter. Continue unfinished work drafts a new request from the recorded facts and shows it to you first, with Not now as its first button. Nothing is resumed or retried on its own. Times on the card are local, with the time zone named. Hover over a time to see the same time in UTC.

Every turn that hands control back to you gets one Request summary card (0.9.94). When a turn you started ends, Chat shows a Request summary · Observed by UnodeAi card right after the item that ended the turn. That item is the reply, or UnodeAi’s own line if the turn ended without a reply. Its summary line reads like Answered · no workspace changes observed · $0.18 · 18s or Verified · 2 files changed · 1 check run passed · 46s. When you open it, it shows nine sections: Result, Work, Changes, Checks, Access & approvals, Context, Team & routes, Usage & timing and Remaining. The first word comes from what UnodeAi observed, never from what the reply says. Answered means that a reply was delivered, not that it is right. Verified appears only when UnodeAi itself ran the configured verification command in that turn and the command exited 0. Where UnodeAi cannot see, the card says so. After a shell command, it reads more possible beside the changed files. A missing price shows as tokens only, never $0. A turn shows one card. The turn that closes a team job shows that job’s Job outcome instead. An earlier turn of the same job reads In progress until the job closes, and Job closed after that. The card is never sent to a model. Showing or opening it runs nothing.

What a turn showed stays when it ends without an answer, and a stopped coordinator ends its job (0.9.94). If a turn ends with no final reply, it keeps every reasoning segment it showed. These stay open and are labelled Work shown; no conclusion recorded, even after a reload. The turn's card reads No conclusion recorded. The text is not turned into an answer, and nothing is sent again. If you stop a coordinator before it has replied in a job, and nothing in the job is still running, the job ends at that point. Its Job outcome appears under the stopped turn. No later message is needed.

A request limit is a stop that you decide (0.9.94). This removes worker fan-out for now, until a hierarchy can keep every child handle visible to its lead.

Coordinator briefs have their own consent setting. A coordinator may attach a short brief, with sources, to one delegated assignment. The worker sees it as a claim by the coordinator, not as host evidence. Its cited inputs must be both declared and granted to that attempt. Otherwise, the dispatch is refused before work starts. A brief can paraphrase your documents, and it travels in the worker’s prompt rather than through a read tool. By default, when the worker’s resolved model destination differs from the coordinator’s, the brief is sent without a pop-up. To be asked for each dispatch, turn off Allow cross-provider dispatch without approval in Settings → More. A modal then names the destination. If you decline, the dispatch is refused. If the destination is the same, UnodeAi never asks. A destination that cannot be resolved is refused. The setting is user-level only, so a workspace cannot change it.

Shared memory is context, not authority. A memory_note appends to .unode/memory/notes.md in the first workspace folder. It writes the routing tier that the host selected, plus a semantic kind that the agent selected (pitfall, contract, or decision). The file can be changed, so once it is reloaded, those fields are recorded claims, not durable proof. Every prompt row is structurally encoded and labelled untrusted by default. Limits on count and bytes apply. contract has no special trust or retention right.

Run UnodeAi: Review Shared Memory to inspect an exact row. Then, as a separate step, you can confirm or revoke a local human-attested label. The host-owned record changes only prompt admission and display. It does not verify truth or identify who clicked. It does not grant tools, folders, commands, network, MCP, delegation, hooks, completion, or evidence authority. Editing one byte invalidates the match. New attestations are refused in an untrusted workspace. Path resolution fails closed if the memory file or a parent link escapes the primary folder. A memory is never automatically promoted to a rule or a skill.

For independent work, the PM uses dispatch_task, shows Delegating · N out, and stays ready for your next instruction. When work comes back while the PM is idle, the PM wakes for one normal turn, with the evidence. The PM can then report or continue on its own. If the PM is busy, the composer says how many delegated results are waiting behind that turn. The model does not wait or poll. collect_ready_tasks is optional and returns only results that have already settled. A result that has settled but has not been delivered also stays available after a session resumes. This does not claim that a worker that was still running has resumed. inspect_task_status keeps the worker, wait-window, result, and read-receipt states separate. Only a ready result names collect_ready_tasks.

An unfinished directed turn settles as partial. Its full report stays visible, and its unfinished structured activity is carried separately. Partial stops the waiting card and wakes the coordinator, but it is never counted as a completed delivery or a green verdict. A workflow keeps the report and pauses before its gate or next step.

A safety-stopped worker continues instead of restarting. OpenAI-compatible agents share an emergency backstop of 100 iterations. Repeated identical calls still stop earlier, through anti-spin. Either stop gets one final model request with no tools. That request is followed by a Stopped: line written by the host and a typed partial result. The PM uses continue_task to resume the same worker conversation and may narrow the remaining focus. The new turn receives a fresh allowance and a new grant bound to the attempt. Authority from the stopped attempt is not revived.

New in 0.9.61: delegation is a host-checked task contract. The coordinator declares the deliverable, separate read and write effects, required capabilities, inputs, constraints, dependencies, verification sensors, and whether the work is delegate-preferred, delegate-required, or coordinator-only. The host filters permissions, task scope, file claims, input grants, artifact readiness, and sensor reachability before it chooses an executor. An exact id that does not fit is refused. Role routing rotates only among the agents that pass. The coordinator gets no looser path, and Solo is never an automatic fallback.

A refusal no longer has to be a dead end. The configured-workspace boundary has not been relaxed. No path becomes newly readable or writable. A real path escape is still blocked and ends the turn. A shell line that merely looks out of root is still blocked and never runs. That check is only a heuristic on the command text, not a filesystem proof, so the agent can still make a different safe call. Likewise, an expired, unsupported, or unforwarded temporary asset is still unavailable. It is refused without ending useful work.

Inputs belong to one execution attempt. A contract can name a content asset supplied in the turn, a workspace path (current, or as snapshotted at dispatch), or an explicit upstream artifact. The worker receives a task card, not the coordinator’s conversation. Ending the attempt revokes its grants synchronously, including across retries. An input never grants write, shell, web, or MCP authority. Only an immutable artifact-ready record can become a downstream dependency. It keeps the complete chain of input provenance.

Missing context is a task state. report_context_gap uses missing, expired, outside-task-scope, or unreadable. The coordinator sees the declared purpose, so it can supply, re-scope, or escalate. The worker and the portable export do not learn whether an unauthorised source exists. Internal evidence keeps the compiled contract and the supplied/reachable/read receipts. It never records “understood”. Portable evidence uses input numbers that are local to the document. It omits the contract prose, paths, source ids, attempt ids, artifact handles, and provenance identities.

The input-substitution rule follows the contract. If a task declares at least one required input, its card tells the worker to report a context gap instead of substituting web content for material that the host could not supply. A task that declares none, including one that declares only optional inputs, is told that no input-substitution rule applies. This is because optional means the work can be completed without that input. If a source must be consulted, declare it required. The card neither grants nor removes web access. That stays the agent’s configured capability.

Stopping work

While anything is running the status bar shows ⏹ Stop N. One click ends every running turn. It appears only while agents are working, so its presence also tells you whether the crew is still going. The same action is also in the Team panel's ⋯ menu as UnodeAi: Stop All Agents. It ends turns. It is not a message asking agents to stop.

Long tasks can arrive in batches. A coordinator can dispatch a long task with delivery set to incremental and its expected sections. The worker saves each completed section with save_task_checkpoint, and UnodeAi writes it to disk before it confirms it. A saved batch is partial work: it grants nothing and extends no wait or budget. A batch is due after 8,000 provider-reported generated tokens or two minutes of working time since the last one; where a connection reports no live count, it shows as unavailable. A Stop wins: later batches are refused, and the batches saved before it are a draft only you open, with UnodeAi: Saved Task Batches…. They stay on this machine for 30 days after the task ended.

An ended turn is not yet a stopped process. The Team panel shows Stopping until UnodeAi sees the agent's processes end, and Stop unconfirmed when it cannot. UnodeAi then does not start that agent again by itself; starting it yourself goes ahead. An agent's CLI that crashes reads Stop unconfirmed too, and is not restarted for you. cancel_task with a handle stops only that task, never a later turn of the same teammate.

A coordinator can stop its own team. broadcast and send_message only deliver a message. A teammate that is already mid-turn finishes anyway. That is why asking a PM to "stop everything" used to get a broadcast, an assurance, and no stop. cancel_task ends a teammate's turn: one assignment by handle, one teammate by name, or the whole team. Two limits are built in. First, a coordinator cannot stop itself, because that would end the turn that makes the call. Second, a solo agent belongs to no team, so you stop it with your own button, not through a coordinator.

Delegation evidence

Required-input receipts are host facts. A settled task records how many required inputs it declared and how many read receipts the host did not observe. A missing receipt is not proof that the worker did not read. Actual access failures keep their own separate reason: missing, expired, outside-task-scope, or unreadable. Timeout and late-terminal snapshots stay separate. This does not reject the work automatically or replace the coordinator’s later decision.

A teammate's Done is not the verdict. Each delegation shows an evidence state derived by the framework, in the Workbench transcript, Activity, and the Team card. The state is Verified, Tool activity recorded; delivery not checked, Replied, not verified, No evidence, Required input read receipt not observed, or Timed out. Completion is a separate fact, so a verified partial result remains both verified and partial. Changed files come from recorded checkpoints. Passing checks come from the actual verifier record. Only a recorded write with a passing check is Verified. Informational work with tool activity is recorded, but the record does not pretend that the framework judged its prose as delivered.

Interrupted work remains visible. If worker continuity ends before a final reply, Activity shows Interrupted — no active worker. It also shows the worker-lost or host-restarted reason, and the last-observed and detected times separately. The row is final and is not counted as active work. An interrupted handle accepts only abandoned or superseded, and each needs a concrete reason. Replacement work supplies replaces_handle and replacement_reason. On admission, the new handle and the original task’s durable link are written atomically. The Interrupted state is not hidden.

Coordinator decisions are captured, not invented. Once the PM has actually decided whether to rely on a settled result, it may record that decision. It can record accepted, rejected, needs-human, and the other documented dispositions for settled results. In v0.9.80, abandoned was added for interrupted work. This is optional. A result that simply arrives is not a decision. Rejection and human-handoff records require a reason. A rejection forwards that reason to the delegate. If an earlier framework verdict is rejected, the Workbench transcript, Activity, and the Team card show a visible amendment and its reason. They do not silently rewrite the earlier line. The framework never uses an LLM or prose sentiment to infer this decision.

The session counter reports completed delegations, explicit coordinator acceptances, green framework verdicts that were later rejected, and explicit human-intervention requests. Coordinator-accepted is not enterprise or customer acceptance. The coordinator is an agent, and this counter measures agent decisions. A separate human verdict was added in 0.9.59, as described below. The two are never merged.

Reviewing delivered work

A run nobody judged reports unjudged, never accepted. UnodeAi: Review Delivered Work shows a finished run’s evidence and asks a person for one verdict: accept, accept with exceptions (at least one open item required), or reject. A rejection is a real measured outcome, not a failure of the tool. Nothing converts a coordinator’s disposition, a green verified outcome, a closed run, or your silence into a human answer.

A run with delegated work still active cannot be judged. It stays unjudged until it settles. Verdicts are append-only. The run reports the later verdict, and the earlier one stays readable. Runs from before 0.9.59 load as unjudged. A verdict needs an approver at the time it is given. The same rule already applied to command and write approvals. In portable evidence, the verdict travels with a count of unresolved items and an approver number that is local to the document. The text you typed and the approver identity do not leave.

Spend: what a request cost, and reminders (0.9.89)

Reminders, never a brake. UnodeAi records the tokens each request used and the best-sourced cost it can honestly show. It can remind you when a target is crossed. Crossing a target never stops, pauses, refuses or shortens work. You decide. UnodeAi: Open Spend opens the Dashboard with its Spend section first.

  • What is counted. Every model turn is counted once. On OpenAI-compatible routes, each completed response that reports usage counts as soon as it finishes, so you can get a reminder while a long tool loop is still running. Claude CLI counts from its final result. Codex CLI counts from the change in its running total for that conversation. After Stop, only observed usage counts. A cut-off response is labelled partial or reconstructed. When nothing attributable arrived, the request shows a coverage gap instead of a guessed amount.
  • Where a cost comes from, each labelled: a cost the provider bills; your exact-model price; an account estimate for this key (its stated coefficient, its stated group, or a group the gateway explicitly ties to the key — exactly one); the gateway's published list price (shown, never used for a reminder); a dated Unode or Roam reference (for a dollar reminder only if you chose it); otherwise price unavailable with tokens. Subscription CLI usage shows an API-equivalent figure and never drives a dollar reminder. Having a stored key, or a list of groups a key may use, never counts as knowing what the key pays.
  • First-run choice. After the first gateway turn with no billed or account price, UnodeAi asks once: Use token reminders only, Use Unode estimate for dollar reminders or Use Roam estimate for dollar reminders. Nothing waits on it, and it makes no sound. Closing it records nothing, and it comes back at most once a week. The choice applies to later turns. The turn that just ended keeps what was recorded. A reference is offered only when its price list has a price for the exact model. A gateway's prefixed name for a model is priced only where the list declares that name.
  • Dated references. The bundled Unode and Roam references were captured on 2026-09-27. Each figure names its date and turns stale after 30 days. You then get one quiet reminder, and after that at most one every 30 days. Update reference prices on the Unode and Roam provider cards, or the two Update … Reference Prices commands, take a fresh anonymous snapshot over HTTPS with no key.
  • Targets (Settings → Spend, User Settings only): per request, a project total per day or month in your time zone, and agent shares. All are off by default.
  • The ladder. At 80%, you get a quiet chat line and a warning. At 100%, 150%, 200% and every further whole multiple, chat shows Over target — work is continuing. If the usage arrives after the work ended, such as for a turn you just stopped, chat shows Over target and says that nothing is running. You also get a status-bar item, a Team badge, the chime, and a dialog with Keep going, Stop this request, View spend, Change target and Reset counter. Each threshold appears once across windows, and no timer repeats it. A jump past several thresholds shows only the highest, and the multiples have no upper limit. If a usage record cannot be saved at once, the Spend section says Usage updating, and UnodeAi retries until it is saved. Stop this request stops only that request's still-running turns, once. Partial, reconstructed and API-equivalent figures never trigger a reminder.
  • Reset starts a counter again from zero (request, project period, one agent, or all). History and receipts are kept, and work is not touched. The ladder can then remind you again.
  • A project can only suggest lower targets. .unode/budget.json is read strictly and shown as one quiet proposal per version (Review / Ignore this project). It has no effect until you accept that exact version. Even then, it only lowers reminders you have already enabled. It can never enable a reminder, pick a reference, reset a counter or make a sound.
  • Savings are priced on both sides from one dated reference, which they name. Otherwise, no savings are claimed.

What your key actually pays

A gateway publishes what a model costs. What your key is charged is settled inside the gateway, and it is often not reported at all. As a result, a published price can be several times what you pay. Worse, it can look right while being wrong.

Two settings cover this, and both belong to the key rather than the account. That is because two keys on one account can sit in different billing groups, with different prices and different callable models.

  • unode.priceGroup — names the billing group, per connection: { "unode": "vip", "roam": "default" }. Where a gateway offers several groups and you have not named one, UnodeAi shows the undiscounted rate rather than guessing the cheapest. An over-estimate is visible, and your first invoice corrects it. An under-estimate takes money without warning.
  • unode.priceMultiplier — what fraction of the published price the key pays: 1 is list price, 0.33 a third of list, 0 free. UnodeAi asks for this when you store a key, because that is the one moment when you have the fact at hand.
  • New in 0.9.78: repairing an old coefficient never blocks the command that triggers it. A legacy key with no stated coefficient is repaired when you open Settings or run Refresh Model Prices. That repair writes to your User Settings JSON. An editor refuses that write while the file has an error or warning. This used to make both commands appear to do nothing. Now the panel opens, and a price refresh reports its result, before the repair is attempted. A failed repair shows a warning with an Open User Settings (JSON) button, instead of swallowing the command.

Exactly one discount is applied. A stated coefficient and a gateway-reported group ratio answer the same question, so applying both would answer it twice. When you set a coefficient, it is the one that counts. This means that a stated 1 deliberately suppresses a discount that the gateway would otherwise have applied. If you leave a connection unset, the gateway answers. Every refresh states in the Output channel which of the two produced the number.

An empty box means list price, and so does Esc. The box opens empty so that an Enter still travelling from the previous key prompt cannot accept a price before you have read the question. Because it opens empty, empty has to carry a meaning. It is never read as free. To mean free, type 0 on purpose.

Prompt caching — the cached number

The Dashboard's Tokens card reads in / out / cached (N%). Cached input is the part of the prompt that your provider served from its own cache. It is billed at roughly one tenth the price. In a long conversation, it is most of what determines your bill.

Caching works on a prefix. Everything before the first byte that changes can be reused. Everything from that byte on is re-read at full price. UnodeAi therefore keeps the stable part of a request — model, tool definitions, system prompt — byte-identical for the life of a session. It attaches state that changes (project rules, shared-memory notes, your open file) at the end of the request. There, changing it cannot invalidate anything before it.

Dashboard status colours follow the active VS Code theme. Working and done use different semantic theme tokens. Where a testing-status token is unavailable, the earlier colour stays as a fallback, so an indicator can never end up without a colour.

Two things are worth knowing:

  • Claude caches nothing unless it is asked to. Every other provider caches automatically. Anthropic requires explicit cache markers in the request. UnodeAi sends them and then checks whether they took effect. This matters because a missing cache does not fail, it only bills. If a route turns out not to cache, the agent's Output channel says so plainly instead of letting you find out on an invoice.
  • cached: not reported is not cached: 0. Some gateways don't pass the cache counter back. UnodeAi says "not reported" instead of showing a healthy-looking zero. Where it can reconstruct the real figure, it labels it an estimate.

To see what one agent's caching is actually doing, open View → Output and pick UnodeAi · <agent>. It stays quiet while caching works, and speaks up when it doesn't.

Choosing a model

The model field is a combobox, not a fixed list. Any id you type is sent to the provider exactly as written, whether or not the picker has heard of it. The suggestions are a convenience, never a limit.

Claude CLI leads with the CLI's always-latest aliases: opus, sonnet, haiku, fable. Each time an agent starts, the CLI resolves the alias to the newest model in that family. Pick an alias to stay current without ever editing settings. Pick a pinned id such as claude-opus-5 when a run has to be reproducible later. An agent on an alias is still costed from the CLI's own reported total. The picker shows no price for an alias, because an alias can name a newer model with a different price.

This matters because you cannot ask a CLI which models it serves. There is no claude models command. An unknown --model prints a warning and still exits 0. As a result, an id can be neither discovered nor verified. A list frozen into the build was wrong again in every release where nobody edited it by hand. That is why claude-opus-5 was once missing from the picker, even though typing it by hand worked fine.

Suggestions come from up to four layers, best first: unode.extraModels (yours, no reload), unode.modelCatalogUrl (a hosted catalog, reload required), the gateway's live /v1/models (OpenAI-compatible routes only, subject to metadata consent), then the built-in defaults.

Security

  • Provider keys are stored in VS Code SecretStorage.
  • A connection owns its endpoint and its key. An agent route stores only an opaque connection ID and a model ID. The extension host resolves the endpoint and the SecretStorage identity from its own registry. A hand-edited team file or a webview message cannot redirect a named gateway to another host. Nor can it make the gateway use another gateway's key. An unknown or removed profile stays a visible repair, instead of falling back to any default gateway.
  • File access is sandboxed to the workspace or the assigned worktree. In Agent Builder, you can narrow individual agents to explicit Read / Read+Write folder grants.
  • Command execution is controlled by unode.commandApproval.
  • Prompted-command frequencies stay local. unode.debug.promptedCommandLog is off by default and user-only. When you enable it for a review period, it records only the narrow CommandPolicy template for an approval prompt that was actually shown. It never keeps raw arguments, URLs, or secrets, and it has no network path.
  • Each command runs in one identified shell (0.9.96). On an OpenAI-compatible or custom-gateway agent, a foreground run_command runs in that agent's own terminal, under your default terminal profile. The approval card names the shell, from your terminal settings or from what the terminal proved last. Nothing is started for a command before you approve it. After the approval, UnodeAi opens the terminal if needed and proves its shell, its starting folder, and that it can read the output. If the shell is not the one on the card, the command is not run. If the terminal cannot be used, the agent's next command runs in a named fallback: cmd.exe on Windows, /bin/sh on macOS and Linux. UnodeAi never switches shells after an approval. The starting folder is checked, but the shell is not a sandbox.
  • Syntax that cannot run in the shell is refused before any approval prompt: a PowerShell cmdlet such as Copy-Item in cmd.exe or a POSIX shell, and && or || in Windows PowerShell 5.1. The refusal names the shell and gives an equivalent. It is never reported as missing consent.
  • One agent's foreground commands run one at a time; different agents run in parallel. A timed-out command's whole process tree is stopped and its terminal replaced. Checking the stop usually takes about a second, and up to a minute on a very busy computer. If UnodeAi cannot confirm the stop, or the terminal closes while a command runs, that agent runs no further commands, in the background either, until you restart it or reload the window. kill_command reports a background command as killed only after UnodeAi saw its process tree end and its output close. When the window closes or reloads, UnodeAi stops every command it started at once and waits for those stops while VS Code lets it; no command starts after that, even one approved before. It does not watch the stops finish, and the output channel names each background command stopped this way.
  • Command approvals belong to one shell grammar: cmd.exe, PowerShell, or POSIX shell. Enable safe commands adds the reviewed list for all three. After an upgrade, a project approval from before 0.9.96 may ask once more, and an old safe list must be enabled again.
  • Claude CLI uses a fail-closed gate before each tool runs. Shell commands keep the command approval, and native writes honor write approval. External or newly introduced Claude tools ask before running, even inside native subagents.
  • Codex CLI uses Codex's native permission model. UnodeAi asks for a separate consent before it starts the App Server process. Act offers Ask for approval, Approve for me, and Full access (unsafe), which you confirm separately. Plan and host ceilings use read-only. Full access removes the sandbox and the prompts. UnodeAi does not control the CLI's network destinations. Nor does it claim that the CLI's reads are confined to the workspace.
  • File writes can require diff approval with unode.writeApproval = ask.
  • MCP servers that UnodeAi manages are denied by default and can require approval before mounting. The Security panel lets you review each agent's MCP grants beside its folder grants. MCP servers you configure directly in Claude or Codex stay under that CLI's own controls.
  • Plan mode removes high-impact tools for OpenAI-compatible agents.
  • Zero data retention & no telemetry. UnodeAi itself keeps no copy of your code or prompts. It has no analytics, tracking, or phone-home. Chat history, config, and keys stay on your machine. Your code is sent only to the model provider you configure. UnodeAi works with any OpenAI-compatible endpoint, so you can point it at a self-hosted / in-VPC model for provable, end-to-end zero-retention.
  • Nothing beacons on install. No metadata path — price server, catalog, balance — contacts a host at activation until you approve one. The consent gate refuses an unapproved host before any packet is sent. (This is enforced in the source and tested. The absolute claim of "zero traffic of any kind" is marked UNVERIFIED in SECURITY.md, pending a packet capture on a clean profile.)
  • Two separate network grants, both revocable. Sending a host your prompts and code (model egress) is one grant. Fetching its price list, model list, and your account balance (metadata — never any code) is another. UnodeAi asks for the second one, with an accurate description, only when you open a model picker or refresh prices. Opening one provider's picker never contacts another provider's gateway. The Security panel lists each grant on its own row, with its own revoke action.
  • Public-web requests are separately controlled. Gateway fetch_url and Claude WebSearch/WebFetch require an agent's read capability and follow unode.webAccess, which defaults to ask. The approval card can allow one request, deny it, or allow the whole crew for this extension session. The session choice is not saved. With off, or without read access, those tools are not advertised. The host still denies a stale direct request. A denial is shown as refused on the tool card. This comes from the host's structured decision and is never guessed from English result text. MCP and subprocess output remains explicitly external.
  • Claude startup consent is actionable. When a native model-egress dialog is open, the agent shows Consent required instead of staying on Starting. Answer the dialog that is already open. Allow resumes the same start, and Cancel reports an error. If you stop the agent first, a later Allow cannot spawn the process.
  • The hosted skill catalog is verified or it is nothing. A remote catalog is merged only if it has a valid publisher signature over its exact bytes. Unsigned or tampered content is rejected, and the bundled catalog stays in place.

Use unode.commandApproval = all only inside a sandbox or disposable environment.

Verified worktree fan-out

For larger parallel jobs, set unode.concurrencyStrategy = worktree (requires a git repo with a clean tree). Each eligible agent gets its own isolated git worktree under .unode/worktrees/. When its turn finishes, its work is committed and merged into a Roam integration branch (unode/integration).

Only work that passes your checks lands. Before merging, UnodeAi runs your unode.verifyCommand (build/lint/test) inside that agent's worktree. If it passes, the work merges. If it fails, the work is held on the agent's own branch and handed back to be fixed. Nothing unverified reaches integration. Neither Cline nor Kilo gates the team merge on verification.

A successful Git command is not automatically a merge. UnodeAi compares the integration branch's HEAD before and after the command. If it did not move, the lane says nothing to merge. If it moved, the lane says merged. This does not depend on Git's display language.

  • Review with UnodeAi: Crew Worktrees (Review). Each lane shows ✓ verified / ✗ failing / ⚠ unverified. A lane that passed by editing the tests (instead of fixing the code) is flagged for review.
  • Land integration work onto your branch with UnodeAi: Finalize Worktree Merges to Branch.
  • The gate is controlled by unode.worktree.verifyBeforeMerge (on by default) and unode.worktree.verifyTimeoutSeconds. With no unode.verifyCommand, there's nothing to gate on, and merges proceed.
  • Control parallelism with unode.worktree.maxParallel. Leave unode.worktree.autoMerge off when you want manual review.
